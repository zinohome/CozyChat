# 文档时效性管理方案

> **状态**: ✅ 活跃 | **最后更新**: 2024-12-22 | **版本**: 1.0.0

## 变更历史

- **2024-12-22 (v1.0.0)**: 初始版本，文档时效性管理方案上线

---

## 问题背景

随着CozyChat项目的持续开发和重构，文档管理面临以下核心问题：

### 问题1: 文档时效性不明确

- ❌ **现状**: 无法判断文档是否过时
- ❌ **现状**: 不知道文档最后更新时间
- ❌ **现状**: 无法追踪文档的修改历史

**影响**:
- 开发者不确定文档是否准确
- 可能基于过时信息做决策
- 浪费时间验证文档有效性

### 问题2: 文档同步更新困难

- ❌ **现状**: 代码重构后，文档没有同步更新
- ❌ **现状**: 旧文档包含错误或过时信息
- ❌ **现状**: 缺乏提醒机制

**影响**:
- 文档与代码不一致
- 新成员可能被误导
- 降低文档可信度

### 问题3: 文档维护成本高

- ❌ **现状**: 270+篇文档，手动维护困难
- ❌ **现状**: 缺乏系统化的维护流程
- ❌ **现状**: 没有优先级分类

**影响**:
- 文档质量下降
- 维护工作混乱
- 浪费人力资源

## 解决方案总览

我们设计了一套**完整的文档时效性管理方案**，包括：

```
文档元数据规范
    ↓
自动化工具
    ↓
检查机制
    ↓
定期维护流程
    ↓
持续改进
```

## 1. 文档元数据规范

### 设计目标

- ✅ 每个文档都有明确的时间信息
- ✅ 文档状态一目了然
- ✅ 易于自动化处理

### 元数据格式

每个文档开头添加YAML front matter：

```yaml
---
title: 文档标题          # 必需
version: 1.0.0          # 必需
created: 2024-11-15     # 建议
last_updated: 2024-12-22  # 必需
status: active          # 必需: active | outdated | deprecated | draft | archived
author: 张军            # 可选
reviewers: []           # 可选
related_code:           # 可选: 关联代码路径
  - backend/app/xxx.py
tags: [标签1, 标签2]     # 可选
---
```

### 文档状态定义

| 状态 | 标记 | 含义 | 使用场景 |
|------|------|------|----------|
| `active` | ✅ | 活跃 | 文档与代码完全同步，可放心使用 |
| `outdated` | ⚠️ | 过时 | 部分内容过时，需要更新 |
| `deprecated` | ❌ | 废弃 | 已被新文档替代，不应再使用 |
| `draft` | 🚧 | 草稿 | 文档正在编写中，内容不完整 |
| `archived` | 📦 | 归档 | 历史文档，仅供参考 |


## 2. 自动化工具集

### 2.1 文档管理器 (`docs_manager.py`)

**功能**:

1. **扫描文档**: 遍历所有.md文件，提取元数据
2. **生成索引**: 创建 `docs/INDEX.md`，按分类列出所有文档
3. **检查过期**: 发现超过30天未更新的文档
4. **生成报告**: 创建 `docs/DOCS_REPORT.json`，包含详细统计

**使用方法**:

```bash
# 扫描所有文档
python3 scripts/docs_manager.py scan

# 生成文档索引（每天运行）
python3 scripts/docs_manager.py index

# 检查过期文档（每周运行）
python3 scripts/docs_manager.py check

# 生成详细报告（每月运行）
python3 scripts/docs_manager.py report
```

**输出示例**:

```
🔍 扫描文档目录...
✅ 找到 270 个文档

⚠️  发现 167 个过期文档（超过30天未更新）:

    路径: architecture/03-前端架构设计.md
    最后更新: 45天前
    关联代码: frontend/src/
```

**生成的INDEX.md**:

## 3. 检查机制

### 3.1 Pre-commit Hook（提交时检查）

**目的**: 确保提交的文档包含完整的元数据

**配置**:

1. 安装pre-commit:
   ```bash
   pip install pre-commit
   ```

2. 配置 `.pre-commit-config.yaml`:
   ```yaml
   repos:
     - repo: local
       hooks:
         - id: check-docs-metadata
           name: 检查文档元数据
           entry: python3 scripts/check_docs_metadata.py
           language: system
           files: \.md$
           pass_filenames: true
   ```

3. 安装hook:
   ```bash
   pre-commit install
   ```

**效果**:

```bash
git add docs/my-doc.md
git commit -m "docs: 更新文档"

# 自动检查
检查文档元数据...................................................✅
```

### 3.2 定期扫描（自动检查）

**每天**: 自动生成文档索引
- 通过Cron job运行
- 发现新增/修改的文档
- 更新 `docs/INDEX.md`

**每周**: 检查过期文档
- 发现超过30天未更新的文档
- 发送通知（邮件/Slack/钉钉）
- 创建GitHub Issue提醒

**每月**: 生成详细报告
- 统计文档数量、状态分布
- 生成 `docs/DOCS_REPORT.json`
- 发送月度报告

### 3.3 CI/CD集成（可选）

**GitHub Actions**:

```yaml
# .github/workflows/docs-check.yml
name: 文档检查

on: [push, pull_request]

jobs:
  check-docs:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      
      - name: 检查文档元数据
        run: |
          python3 scripts/check_docs_metadata.py $(git diff --name-only origin/main...HEAD | grep '\.md$')
      
      - name: 检查过期文档
        run: |
          python3 scripts/docs_manager.py check
```

## 4. 维护流程

### 4.1 创建新文档流程

```
1. 复制模板
   cp docs/.template.md docs/category/新文档.md

2. 填写元数据
   - 标题、版本、日期
   - 状态设置为 draft

3. 编写内容
   - 按模板结构编写

4. 完成审查
   - 更新状态为 active
   - 提交代码
```

### 4.2 更新现有文档流程

```
1. 修改文档内容

2. 更新元数据
   - 小修改: 更新 last_updated
   - 大修改: 更新 version + last_updated

3. 记录变更历史
   - 在变更历史中记录修改

4. 提交代码
   - Pre-commit自动检查
```

### 4.3 文档生命周期

```
创建
  ↓
草稿 (draft)
  ↓
审查
  ↓
活跃 (active)
  ↓
代码变更 → 更新文档 (active)
  ↓
内容过时 (outdated)
  ↓
重写或废弃 (deprecated)
  ↓
归档 (archived)
```

### 4.4 定期维护任务

**每天**:
```bash
# 自动运行（Cron）
./scripts/docs_maintenance.sh daily
```

**每周**:
```bash
# 自动运行（Cron）
./scripts/docs_maintenance.sh weekly

# 手动: 更新1-2个过期文档
```

**每月**:
```bash
# 自动运行（Cron）
./scripts/docs_maintenance.sh monthly

# 手动: 审查核心文档
# 手动: 清理临时文档
# 手动: 归档废弃文档
```

## 6. 最佳实践

### 6.1 代码变更时同步更新文档

```markdown
PR检查清单:
[ ] 代码修改完成
[ ] 测试通过
[ ] 相关文档已更新:
    [ ] 更新文档内容
    [ ] 更新 last_updated
    [ ] 更新版本号（如需要）
    [ ] 在变更历史中记录
[ ] Pre-commit检查通过
[ ] 提交（代码 + 文档）
```

### 6.2 优先级分类

| 优先级 | 文档类型 | 更新要求 | 检查频率 |
|--------|----------|----------|----------|
| P0 | 核心文档（架构、API） | 必须与代码同步 | 每次代码变更 |
| P1 | 功能文档 | 重要功能需更新 | 每周检查 |
| P2 | 参考文档 | 可容忍一定滞后 | 每月检查 |
| P3 | 临时文档 | 不强制更新 | 定期清理 |

### 6.3 团队协作

**原则**: 谁改代码谁更新文档

**流程**:
1. 开发者修改代码
2. 开发者更新相关文档
3. Code Review时检查文档
4. 合并前确保文档同步

### 6.4 处理过期文档

**临时方案**（如果没时间立即更新）:
1. 更新状态为 `outdated`
2. 添加警告提示
3. 创建TODO issue

**长期方案**:
1. 定期审查和更新
2. 设置提醒（每周/每月）
3. 分配责任人

## 9. 常见问题

### Q1: 如何处理历史文档？

**分批处理**:
1. **第一批**: 核心文档（架构、API）- 立即添加元数据并更新
2. **第二批**: 重要功能文档 - 1周内完成
3. **第三批**: 参考文档 - 1个月内完成
4. **第四批**: 临时文档 - 标记为draft或删除

### Q2: 文档太多，维护不过来？

**优先级策略**:
- 核心文档: 必须保持最新
- 功能文档: 按使用频率排序
- 参考文档: 可容忍滞后

**自动化帮助**:
- 使用工具自动检查
- 设置定期提醒
- 团队协作分担

### Q3: 如何确保开发者遵守规范？

**强制机制**:
- Pre-commit hook自动检查
- CI/CD中检查失败则不允许合并
- Code Review检查文档

**激励机制**:
- 文档质量纳入绩效
- 定期表彰文档贡献者
- 建立文档文化

### Q4: 工具出问题怎么办？

**应急方案**:
- 保留手动检查流程
- 工具代码有注释和文档
- 团队成员都了解原理

**故障恢复**:
- Git历史可回滚
- 文档备份
- 工具Bug修复
